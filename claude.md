# CLAUDE.md

Project context for Claude Code. Read this before making changes. Keep it updated as decisions change — this file is the source of truth for "why," not just "what."

## What this project is

A hackathon Agent platform middleware challenge. We start from a working Starter Kit (Agent CRUD, Playground chat, Codex CLI execution in disposable containers, BytePlus ModelArk model connection, local JSON persistence) and build ONE coherent middleware story on top of it.

**Do not rebuild the baseline.** Out of scope unless explicitly told otherwise: the React app shell, the CRUD API, the Playground, the Codex integration itself, the container launcher, cloud/multi-region infra. If a task seems to require touching one of these, stop and ask rather than assuming it's in scope.

## Our chosen middleware story

Two related capabilities:
1. **Identity & Authorization** — per-agent identity, server-side authorization enforcement, action attribution, credential rotation/revocation, audit trail. Status: **working**, currently in incremental-improvement mode (see Current priorities).
2. **Multi-agent orchestration** — agents take turns in a coordinated sequence (demo case: counting down 10→1, alternating turns). Status: **buggy**, actively being fixed.

These two features should integrate with each other where possible (e.g., orchestration turns get logged into the same audit trail as authorization decisions) rather than existing as two disconnected demos.

## Evaluation criteria (design against this, always)

| Category | Weight | What it rewards |
|---|---|---|
| End-to-end middleware behavior | 40% | Real frontend→backend/Runtime/data path with functional evidence. Server-side enforcement, not UI cosmetics. |
| Technical design and integration | 25% | Clear rationale, coherent architecture, one clear boundary owner, extensible contracts. |
| Verification and robustness | 20% | Automated tests, error handling, cleanup/recovery, redaction, resistance to obvious bypasses. |
| Demo and reproducibility | 15% | Concise live demo, useful README, one-command startup, documented limitations, no hidden manual setup. |

Rule of thumb: a UI-only fix (hiding a button, showing a fake success state) scores near-zero on the 40% category no matter how polished it looks. Prefer a real backend check with a working test over a good-looking screen.

## Key technical decisions already made (don't relitigate without discussion)

- **Secret handling**: reversible encrypted secret storage is used (not one-way hash) because live key injection into the agent runtime requires the plaintext key at execution time. This is a deliberate tradeoff — flag it as a documented limitation in the README, don't "fix" it into a one-way hash without checking whether that breaks key injection.
- **Password/credential hashing** (where one-way is correct, e.g., any user-facing auth secret that never needs to be recovered): use **scrypt**.
- **Naming convention**: camelCase everywhere in code (variables, functions, JSON keys). Don't introduce snake_case in new files.
- **Credential rotation model**: hard-cutover rotation, not gradual/dual-key rollover. This fits the per-run container model — each run gets a fresh container, so there's no long-lived process holding an old key across the rotation boundary. Don't build dual-key grace-period logic; it solves a problem we don't have here.
- **Authorization enforcement boundary**: a single shared middleware function, `checkAgentCredential()`, is the one place authorization decisions get made. Any new authorization check should call into this, not duplicate logic elsewhere. If a new feature needs a check this function doesn't support yet, extend the function — don't add a parallel check path.

## Current priorities (in order)

1. **Fix multi-agent orchestration turn-taking.** This is broken and demo-blocking. See `claude-code-prompt-phase2.md` for the full diagnostic + fix + test spec. Diagnose root cause before patching; don't hardcode the 10→1 case.
2. **Audit identity & authorization against the rubric above** and apply high-value, low/medium-effort fixes only. Large-effort gaps get written up as documented limitations, not attempted mid-hackathon. Full checklist is in `claude-code-prompt-phase2.md`.

If time runs out, stop after priority 1 and report status rather than starting priority 2 partway.

## Working conventions

- **Diagnose before fixing.** For any bug, state the root cause (with file/function) before writing a patch. Don't shotgun-fix symptoms.
- **Test the middleware, not the UI.** Every fix to authorization or orchestration needs an automated test that exercises the actual enforcement/logic path, not a UI smoke test.
- **Show failure, not just success.** The rubric explicitly wants a denial/failure/recovery case demonstrated, not just the happy path. When adding a feature, ask "what's the failure case I should also demonstrate?"
- **No hidden manual setup.** Anything needed to run the demo (seed data, env vars, mock users) must be scripted into the one-command startup, not a README instruction to "first go run this by hand."
- **Never commit or print secrets.** API keys, AK/SK, tokens, and passwords must be redacted in logs and UI. If you're about to log a payload that might contain one of these, redact it first.
- **Report before big changes.** If a fix requires touching baseline/out-of-scope code, or requires a schema change that affects both identity/auth and orchestration, stop and summarize the tradeoff before implementing.

- **Repo layout**: the live working copy is `updated/SmallPotato/` (has `claude.md`, `claude_phase2.md`, `apps/server/src/team-task-service.ts`). The sibling `SmallPotato/` is an older lineage — ignore it. npm workspaces: `apps/server` (`@launchpad/server`, Fastify + vitest) and `apps/web` (`@launchpad/web`, React/Vite).
- **Orchestration / turn-taking logic**: `apps/server/src/team-task-service.ts` — `TeamTaskService`. Model is Lead + Specialists ("Team Task"). `runLoop()` is the sequential turn engine; `executeWithRetry()` runs one agent turn with 1 retry; `applyLeadDecision()` picks the next agent; `applySpecialistResult()` hands the turn back to the Lead. `buildPrompt()` builds Lead vs Specialist prompts + shared transcript, branching on turn policy. Turn state lives on the `TeamTask` row: `currentAgentId`, `currentAssignment`, `turnCount`, `sharedState`, `threadIds`. Limits: `MAX_TURNS=30`, `MAX_COLLABORATION_ROUNDS=12` (the round cap applies to `facilitated` only). A `sequential` run needs `2N+1` turns for an N-step sequence, so the 30-turn cap bounds sequential sequences at N≈14 — fine for the countdown demo, documented as a limitation for longer runs.
- **Turn policy** (`TeamTask.turnPolicy`, `types.ts`) — `null` at creation; the **Lead commits it on its first turn** via `decision.plan.turnPolicy` (mode-agnostic "planning" prompt on turn 1; `applyLeadDecision` locks it in and emits a `coordination_plan` event; later `plan`s are ignored). `"facilitated"` — Lead names the next specialist via `decision.agentId` each turn (open-ended work). `"sequential"` — engine rotates the roster via `nextSequentialSpecialistId()` (round-robin on the count of `delegated` events); Lead only writes the assignment + decides when to `complete` (countdowns / relays / ordered pipelines). The user never picks this. Fix for the P1 turn-taking bug (commit `4e9a612` had deleted the deterministic scheduler).
- **Agent selection** (`TeamTask.agentSelection`, `CreateTeamTaskInput.agentSelection`): `"user"` (default) — the user picks the specialist pool. `"lead"` — user picks only the Lead; `createTask` reserves **every** ready Agent, and the Lead's turn-1 `plan.rosterAgentIds` narrows `specialistAgentIds` to its chosen roster (`releaseAgentsExcept()` frees the rest). Safe because of the existing single-active-team-task lock. `resolveRosterRefs()` is lenient: roster entries given by name or id are resolved against the pool, and unresolvable ones (a hallucinated name, or the Lead naming *itself*) are **dropped**, not fatal — the turn only fails if fewer than `min(2, pool)` valid Agents remain, and then `lastError` lists the exact pool names so the retry can succeed.
- **Sequential output shape**: the sequential Lead prompt phrases each assignment as `… Reply with only: X`, and the sequential specialist prompt forbids any framing (no "Research confirms…"). Belt-and-braces: `tightenSequentialMessage()` in `applySpecialistResult` shortens a chatty `message` back to the bare `X` for the chat when `X` is clearly present (only ever shortens).
- **Lead-output tolerance** (`team-task-service.ts`): the Lead frequently refers to Agents by **name** not UUID and emits odd `turnPolicy` casing / a `null` `agentId` — `resolveAgentRef()` / `resolveRefs()` accept id-or-name against the authorized pool, `turnPolicySchema` normalises casing, and `optionalAgentRefSchema` coerces null/empty to absent. `parseLeadDecision` / `parseSpecialistResult` throw the specific Zod issue (`describeIssues`) and `extractJson` pulls the first `{…}` out of chatty output. If a turn still fails twice it pauses with that specific reason in `lastError`.
- **`resolveAgentRef()` fuzzy matching** (`team-task-service.ts`): the facilitated turn check no longer pauses on a decorated name. `resolveAgentRef(pool, ref)` tries exact id → normalised exact name (`&`→`and`, drop `(…)` asides / a leading `the|a|an|agent|specialist|lead` / non-alphanumerics) → **unique** substring either direction → **unique** token-overlap. Ambiguous ⇒ still `null` (the caller steers, never guesses). When the facilitated `decision.agentId` is missing / unresolvable / the Lead itself, the thrown error is now corrective — it names the exact pool via `describePool()` (names + ids) and tells the Lead to complete if none fits; that text lands in the `turn_retry` event, which is in the transcript, so the attempt-2 prompt is informed. Genuine off-pool picks still pause after the retry. Tests: `team-task-service.test.ts` — "rejects a Lead selection outside the authorized specialist pool" (asserts the steered message), "recovers when the Lead names an authorized specialist with a decorated name".
- **Orchestration HTTP routes**: `apps/server/src/app.ts` — `POST /api/team-tasks` body: `{objective, leadAgentId, specialistAgentIds (>=1 unless agentSelection==="lead"), agentSelection?, resourceId?}` (strict). Route now passes `actorFor(request)` as the first arg to `createTask`. `GET /:id` → `{task, events, eventsVerified}`. `/:id/stop`, `/:id/resume`. Wired in `apps/server/src/index.ts` (`TeamTaskService` now also takes `security`).
- **Team Task tenant isolation**: Agents, Team Tasks, and their conversation transcripts are strictly per-user — only protected *files* cross accounts (via shares). `listTasks(actor)` filters by `ownerUserId`; every task route (`GET /:id`, `/:id/stop`, `/:id/resume`) calls `TeamTaskService.assertTaskOwner(actor, id)` first (404, never 403, so a stranger's task never leaks its existence). `createTask` rejects a `leadAgentId`/specialist the actor doesn't own (`validateAvailableAgents(actor, ids)` → 404 "Selected Agent not found"), and `agentSelection:"lead"` only ever reserves the actor's own ready Agents. `getTask(id)` stays unchecked for the internal engine loop. Test: `team-task-service.test.ts` — "keeps each user's Agents and Team Tasks private to their own account".
- **Team Task protected-resource enforcement** (`team-task-service.ts`): `createTask` runs a **pre-flight** before any workspace/Agent reservation, so a denial means the Lead never runs and no hand-off happens. `resolveRequiredResource(actor, objective, explicitId)`:
  - **Explicit attach** → `{resourceId, resourceName}`; a vanished id ⇒ `403 {code:"RESOURCE_ACCESS_DENIED", reason:"RESOURCE_NOT_FOUND"}`. This is the *only* case that returns non-null / proceeds.
  - **Nothing attached, but the objective refers to a protected doc** → always throws at the start. Name matching is plural-tolerant: `stemTokens()` (`stemWord` strips `ies→y`, trailing `e?s`, skips `<4` chars / `-ss`) then a **contiguous token-sequence** match of the resource name inside the objective (so "what's in the partnership brief" ⇒ "Partnerships Brief"); single-word names need a ≥ 5-char stemmed token. >1 distinct match ⇒ `422 {code:"MULTIPLE_RESOURCES_REFERENCED"}`. Exactly one match: `422 {code:"RESOURCE_NOT_ATTACHED", resourceId, resourceName}` if the actor could attach it (`ownedByCurrentUser || sharedWithCurrentUser`), else `403 {code:"RESOURCE_ACCESS_DENIED", reason: SHARE_MISSING|SHARE_REVOKED|SHARE_EXPIRED}`. No name match but a generic phrase (`GENERIC_RESOURCE_HINT` — "Bob's document", "the shared file", "the report", …) ⇒ `422 {code:"RESOURCE_NOT_ATTACHED"}`. No reference at all ⇒ `null`, task runs with no resource.
  Then, for an explicit attach only: resolved resource + `agentSelection:"lead"` ⇒ `400 {code:"RESOURCE_WITH_LEAD_SELECTION"}`; `preflightResourceAccess()` — non-container runtime ⇒ `409 {code:"RESOURCE_RUNTIME_UNAVAILABLE"}`; then `security.authorizeResourceRead(actor, specialist, id)` for **each specialist** (a hash-chained receipt each), first deny ⇒ `403 {code:"RESOURCE_ACCESS_DENIED", reason, decisionId, resourceId, resourceName, agentId, agentName}`, nothing created. The Lead is not pre-checked (it never reads the file). Per **turn**, `authorizeSpecialistTurn()` still re-runs `authorizeResourceRead` for the acting specialist (mid-task share-revoke / lease-expiry ⇒ `pauseTask`). Tests: `team-task-service.test.ts` — "refuses to start …", "stops before any hand-off when the objective names a protected resource the user cannot access", "stops when the objective mentions a protected document but none is attached", "stops at the start when the objective names an accessible resource (plural-tolerant) that wasn't attached", "mounts … read-only …", "authorizes a specialist turn against another user's resource via a cross-user share".
- **Orchestration UI**: `apps/web/src/TeamTaskView.tsx` — chat-first: a 340px sidebar of collapsible `<details>` panels ("Start a task", "This task", "Activity log", "History") + a large conversation panel that fills the rest. Polls `/api/team-tasks/:id` every 400ms while running. Conversation shows per-agent `specialist_result` bubbles **only when `turnPolicy === "sequential"`**; `facilitated` shows just the objective + final answer. Everything else (steps, `coordination_plan`, retries, tamper-check state) lives in the "Activity log" panel. Copy is deliberately de-jargoned via `STATUS_LABEL` / `EVENT_LABEL` / `modeText` (no "shared state / turns / handoffs / round-robin" in user-facing text). Layout tokens in `:root` (`--sp-*`, `--fs-*`, `--r-*`); the whole `.team-*` block in `styles.css` was rewritten (chat-first 2-col, responsive at 1024/640). Types in `apps/web/src/types.ts`.
- **Orchestration tests**: `apps/server/src/team-task-service.test.ts` (uses a `ScriptedRunner`; helpers `planFacilitated` / `planSequential` build the Lead's turn-1 response). Covers: Lead committing sequential vs facilitated on turn 1 and it being locked, deterministic countdown starting at the first value, range/pool generalisation, mid-sequence error recovery, "Lead picks agents" reserve-then-release, roster validation, facilitated "plan an event", hash-chain tamper detection.
- **Agent runner abstraction**: `AgentRunner` interface in `types.ts`; real impls `codex-runner.ts` / `container-codex-runner.ts`, chosen by `runner-factory.ts` (`createRunner`). Shared by single-agent Playground and Team Tasks.
- **Identity / authorization**: `apps/server/src/security-service.ts` — `SecurityService` (NOT a function called `checkAgentCredential()`; CLAUDE.md's name is aspirational). Key methods: `resolveSession()`, `requireAgentOwner()`, `authorizeResourceRead()` (the per-resource grant check — the single enforcement boundary), `authorizeTeamResourceRead()` (loops the former over a participant set for Team Tasks), `actorForUser()` (rebuild a `RequestActor` from a stored user id, for long-running coordinators), `createGrant()`/`revokeGrant()`. Session/actor plumbing in `app.ts` (`actorFor`, `authenticate`).
- **Audit trail**: `apps/server/src/audit.ts` — `receiptHash`/`verifyReceiptChain` for authorization `decisions` (stored via `SecurityService`, exposed at `app.ts` decision routes + CSV export; UI in `apps/web/src/App.tsx`), plus a shared `chainHash(payload, prev)` primitive. Orchestration turns are `teamTaskEvents`, now hash-chained with that same `chainHash` in `TeamTaskService.addEvent()` and verified by `verifyEventChain()` (surfaced as `eventsVerified` on the task detail route). Full merge into the single `decisions` chain is still a possible follow-up (would be a cross-feature schema change).
- **Cross-user resource sharing**: `ResourceShare` rows (`types.ts`, `database.shares`, schema v6) let a resource OWNER grant another user read access. Model chosen: **share is sufficient** — once an active share to a user exists, *any* Agent that user owns may read the file; there is no separate per-Agent lease step for shared-in resources (leases stay for the owner's own resources). `authorizeResourceRead()` in `security-service.ts` is still the single boundary: after Agent-ownership and resource-existence checks it branches on `resource.ownerUserId === actor.userId` → `GRANT_*` (existing lease path); else → `SHARE_ACTIVE`/`SHARE_MISSING`/`SHARE_REVOKED`/`SHARE_EXPIRED`. `PolicyDecision` gained `resourceOwnerUserId` (denormalized) and nullable `agentId/agentName/agentPrincipalId` so share **management** actions (`action: "share" | "unshare"`, reasons `SHARE_CREATED`/`SHARE_REVOKED_BY_OWNER`) chain into the same receipt log. All receipts minted via one helper, `appendDecision()`. New `SecurityService` methods: `listShareableUsers`, `listSharesForOwner`, `listSharesForResource`, `createShare` (owner-only; optional `expiresAt`, capped at 90d; 409 on duplicate active share), `revokeShare` (owner-only), `listAccountReceipts` (decisions where the actor is human OR resource owner). `deleteResource` cascades: revokes dependent shares + emits `unshare` receipts (like it already did for grants). Routes in `app.ts`: `GET /api/users/shareable`, `GET /api/account/shares`, `GET|POST /api/resources/:id/shares`, `DELETE /api/resources/:id/shares/:shareId`, `GET /api/account/receipts(.csv)`. Team Tasks inherit this for free — `authorizeSpecialistTurn` calls `authorizeResourceRead`. UI: `App.tsx` "Protected resources" tab gains a per-resource Share panel + shares list; a new account-level **"Sharing"** view (`view === "sharing"`) shows share/revoke receipts, reads on your resources, and your reads on shared files. Both resource pickers (single-agent Playground and `TeamTaskView`) list owned **plus** actively-shared-in resources — `App.tsx` passes `accessibleResources` (`ownedByCurrentUser || sharedWithCurrentUser`) to `TeamTaskView`, not just `ownedResources`. **Limitations** (documented): read-only (no write sharing); only the owner can share (no re-sharing by a grantee); a share is user-wide across all the grantee's Agents (no per-Agent targeting).

- **Persistence**: `apps/server/src/store.ts` — `JsonStore`, single JSON file, schema-versioned with migrations (currently **v6**: adds `database.shares`, backfills `PolicyDecision.resourceOwnerUserId`, rebuilds the receipt hash-chain via `rebuildDecisions()`). `store.test.ts` covers migrations incl. v5→v6.
- **Demo seeding** (idempotent, on server start): users `alice`/`alice-potato` + `bob`/`bob-potato` and **three** protected-resource fixtures in `SecurityService.initialize()` (Alice's "Launch Plan", Bob's "Finance Report" — deliberately left un-shared for the denial demo — and Bob's "Partnerships Brief", which is seeded **shared to Alice** so the granted-access happy path is live on startup); the same seven ready Agents (`DEMO_AGENTS` — Trip Coordinator + 3 relevant + 3 deliberately-irrelevant travel specialists) seeded **per demo user** (Alice and Bob), real UUID ids, deduped by name, in `AgentService.seedDemoAgents()`; skipped when `config.nodeEnv === "test"`. So `npm run poc` → sign in → both demos work with zero manual setup. Note: `APP_AUTH_TOKEN` must be **empty** for the local demo (the web UI has no token-entry screen) — see `.env.example`.
